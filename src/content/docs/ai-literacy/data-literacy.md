A model knows only what it learned in training, so the organization's **data**, such as its documents and records, has to reach it through the **context**, everything the agent sends it with a task. Finding the right data for a task is called **retrieval**, and adding it to the context so the model can respond with it is **retrieval-augmented generation (RAG)**. Retrieval relies on a **data pipeline** that prepares data and on three ways to find it: **semantic search** for documents such as specifications, a **semantic layer** for records such as orders, and a **knowledge graph** for links between things such as suppliers and products.

1. **Data pipeline.** It runs **ETL**: it extracts data from source systems, transforms it for retrieval, and loads it into a store. This repeats regularly, so the store keeps up with the sources. The store is a copy, so the permissions of the sources do not protect it. For documents, the pipeline splits the text into **chunks**, parts short enough to be found and read on their own, turns each into an **embedding** that numerically represents its meaning, and loads them into a **vector store**, a database that can compare them.
2. **Semantic search.** It finds chunks by meaning, so a question about refunds also finds a chunk about returned payments. The question gets an embedding too, and the search returns the chunks with the closest ones.
3. **Semantic layer.** It holds business definitions, such as what counts as revenue, and calculates numbers from them. Without it, the model writes database queries itself and guesses the meaning from table and column names, so the same question can get different numbers.
4. **Knowledge graph.** It holds facts as links between things, such as which supplier delivers which product. It relies on an **ontology** that describes which kinds of things exist and how they relate, giving the graph its structure. The model follows the links to answer questions that span systems, rather than piecing answers together from separate searches, which can miss links.

The choice between a vendor's solution and one the organization runs starts with the data it would hold. With a vendor, the **data terms** decide what happens to it: whether it is used for training, how long it is kept, and in which region it is processed. When a vendor already holds the data, such as in a document system with its own search, only its terms for AI features need a check. The organization's own solution is needed only where these terms fall short or the vendor's solution does not cover the sources. Either way, the organization stays responsible for the content: which sources are correct, what business terms mean, and who may see what.

:::tip[Takeaways]

- **Permissions must follow the data.** A copy without them can show anyone what only some may see.
- **Match the approach to the need.** Semantic search finds documents, semantic layers calculate numbers, and knowledge graphs follow links.
- **Content needs owners.** A vendor can run a solution, but only the organization can decide what is correct and what it means.

:::

## Data pipelines

A **data pipeline** turns source data into a copy that is ready for retrieval. The same approach loads records into a data warehouse, and those pipelines often exist already, so the new work is usually in documents. Most of the cost is choosing and cleaning sources and keeping the pipeline running.

1. **Extract.** The pipeline reads documents from source systems together with their **metadata**, such as the title, owner, date, and permissions, so that search can filter by it and answers can name their source. Choosing sources matters more than covering all of them: drafts and duplicates compete with the right answer, so the team picks sources that someone keeps correct. Sources that outsiders can write to, such as support tickets, are added only when needed, because their text can carry instructions that the model may follow.
2. **Transform.** The pipeline turns documents into plain text, splits the text into chunks, and turns chunks into embeddings with a specialized **embedding model**. Chunk size is a trade-off: a chunk that is too short loses the surrounding text that explains it, and one that is too long mixes topics, so its embedding matches none of them well. Embedding costs little, but when a vendor runs the model, the vendor's data terms apply to every document.
3. **Load.** The pipeline writes chunks, embeddings, and metadata to the vector store, which can be a separate product or an extension of an existing database. On later runs, it updates changed documents and removes deleted ones. Embeddings from different models cannot be compared, so changing the embedding model means embedding and loading everything again.

A data pipeline creates a new copy of the data, separate from its sources: their permissions do not protect it, and their changes do not reach it on their own. For security, each chunk keeps the permissions of its document as metadata for search to apply. Where permissions cannot be kept, it is safer to copy only what everyone who can search may see. For reliability, each chunk also keeps its **provenance**, a record of where it came from, such as the source and date, and its **ownership**, who is responsible for the content, so answers can be checked and errors fixed in the source. For operations, regular runs keep the copy and its permissions current, deletions and retention rules remove chunks, and monitoring catches failed runs, which are easy to miss because search keeps working on the old copy.

## Semantic search

**Semantic search** finds the chunks that are closest in meaning to a question. It usually returns the closest chunks even when none of them holds the answer, so finding them is only the first step.

1. **Match.** The search compares the embedding of the question with those of the chunks, so both have to come from the same embedding model. This is fast even on large collections, but embeddings handle exact terms, such as error codes or contract numbers, poorly. **Hybrid search** adds a keyword search, which finds exact words, and combines both results.
2. **Filter.** The search matches only chunks with the right metadata, such as one product, a recent period, or what the person or agent may see. Most vector stores can filter, but permissions take more: the search has to know who asks and which groups they belong to, usually from the organization's identity system. Permissions cannot be left to instructions, because whatever is in the context can end up in the response.
3. **Rank.** A close chunk can be on the topic without answering the question. A **reranker**, another specialized model, reads the question together with each chunk and orders the chunks by **relevance**, how well they answer it. This improves quality but adds cost and latency to every search, so it runs only on the chunks that matching returned. Only the top few go into the context, because extra chunks raise the cost and distract the model. Chunks that are not relevant enough are left out, even if none remain, so the model can say that it has no answer.

In basic RAG, one search runs before the model responds. In **agentic search**, the model decides what to look for and when to search again, which finds more but takes more steps. Search is not always needed: when documents are few and stable, **cache-augmented generation (CAG)** puts all of them into the context, and the platform that runs the model caches them, so repeated requests cost less. A **semantic cache** uses matching for another purpose: it reuses a past answer when a similar question comes, which saves a request, but a similar question can need a different answer, and the past answer can hold what the person asking now may not see.

## Semantic layers

A **semantic layer** stands between the model and the databases, usually a data warehouse. It offers business terms for the model to choose from, instead of tables and columns whose meaning it would have to guess.

1. **Definitions.** A **dataset** is data that the layer covers, such as orders or customers, and **relations** connect datasets, such as each order to its customer. A **metric** is a number calculated from them, such as net revenue as orders minus refunds, and a **dimension** is a property to split or narrow it by, such as region or month. Descriptions and synonyms tell the model that "sales" means net revenue. Departments often count the same thing differently, so each definition needs ownership, and agreeing on definitions is usually the main cost.
2. **Queries.** A query asks for metrics and dimensions, such as net revenue by month in one region. The layer calculates it from the definitions, so the same query is always calculated the same way. The alternative is **text-to-SQL**, where the model writes database queries on its own: it can try any question, but a wrong number can look right. The layer answers only what is defined, so its coverage grows with the definitions. The model can still pick the wrong metric, such as gross revenue instead of net, so answers should name the metrics behind them.
3. **Permissions.** The layer filters data itself, by rules that depend on who asks. Rules on rows decide which records count, so a regional manager gets the numbers of one region, and rules on columns hide fields such as salaries. The rules are kept in the layer or in the data platform that stores the data, and they apply to every query, so the model cannot skip them. They work only if the identity of the person or agent reaches the layer: with one shared account, everyone gets what that account can see.

A semantic layer can be part of a reporting tool, part of a data platform, or a separate product over several of them. Most offer tools to agents through MCP servers, and the approaches differ in who builds the query. With **named metrics**, the model picks metrics and dimensions by name, and the layer builds the query, which gives the most control but needs every metric defined first. With a **query language**, the model builds the query over the definitions, which is more flexible but easier to get wrong. With **question and answer**, the layer's own agent takes the question and builds the query, which is the simplest to use but adds the cost of that agent and hides how it chose the metrics.

## Knowledge graphs

A **knowledge graph** stores facts as things and the links between them, so one answer can draw on several systems. It pays off for questions that take several links. For simple lookups, semantic search is about as good and cheaper to build.

1. **Ontology.** It lists the kinds of things, such as customers and orders, the links allowed between them, such as a customer placing an order, and rules, such as every order having one customer. This gives them one meaning across systems: customers in sales and accounts in billing become one kind of thing. Departments have to agree on it, and it changes as the business does, so it needs ownership. It can start small, with the things that the most valuable questions need.
2. **Facts.** An ETL pipeline usually fills the graph with facts, such as one customer placing one order, and most of the work is in the transform step. Records are mapped to the ontology through their keys, such as the customer number on an order. Documents need a model to extract facts, such as which supplier a contract names, which costs more and can produce wrong facts. The hardest part is **entity resolution**, matching the same thing, or entity, across sources, such as one company listed under two names: a missed match hides links, and a wrong one connects things that have nothing in common.
3. **Queries.** A query follows links from one thing to the next, which is called **traversal**, such as from a supplier to its products, their orders, and the customers behind them, or from a software service to everything that depends on it. The links followed can be shown with the answer, so people can check it. Results grow with every link, so queries need a limit on how far they go. Permissions on things and links decide what each person or agent can follow, but a graph that copies its sources does not inherit their permissions.

Approaches to knowledge graphs differ in how the facts get in. With **GraphRAG**, a model extracts them from documents, and the search follows links from the matching chunks, which takes the least work from people but adds the cost of running the model over every document and leaves the facts unchecked. With a **graph database**, a pipeline loads them, and the model explores them by writing its own queries, which is the most flexible but leaves the ontology and the facts to the team. With an **ontology platform**, the ontology is mapped to existing data, in some cases without copying it, and can come with actions, such as approving an order, which suits business processes but ties the organization to the platform.
